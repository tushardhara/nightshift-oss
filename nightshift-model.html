You write a paragraph. It derives the rest.

Brief → PRD → definition of finished → milestones

.omni/brief.md is the only file a human authors: what should exist, who for, what working looks like, hard constraints, and what is explicitly out this time. There is no goal to write and no completion condition to phrase — producing those is the org's first job, and it is the highest-leverage work it ever does, because everything downstream optimises toward the definition it writes.

Nothing in discovery asks you a follow-up question. Ambiguity gets resolved in the direction most likely to be right, and the assumption is written down where you can see it — numbered, each with what breaks if it is wrong.

The seam count sets the org, not the roster

architect reports how many places work can proceed without collision. Two seams means two crews run, whatever the roster holds — the rest get a grant of zero and say so in the report. Crews queueing on the same files look busy and deliver nothing.

Then it finishes, and stops

docs/prd/DEFINITION-OF-DONE.md is the project's only fixed point — numbered conditions, each observably true or false. Conditions are never quietly edited; revising one takes a changelog line and evidence from delivery. Every milestone closes by verifying its exit criteria against the default branch as it now stands, not against what crews reported, and ends in something a person can actually see working.

When every condition is met, the finish skill writes docs/HANDOVER.md — verified by running the setup from a clean clone — posts the final report, deletes its heartbeat task and stops dispatching. Three legitimate endings, each named in the first line of STATUS.md: complete; complete with exceptions, every dropped condition listed with its reason; or blocked, naming exactly what is needed and what was finished around it. An org that keeps polishing after done is spending your quota on work nobody asked for.

What breaks when you add the third crew

Five bugs that only appear at N > 2

A two-crew design hides its own scaling faults. Each of these was real, and each fix is a mechanism rather than a rule anyone has to remember.

Bug → mechanism
What breaksWhy it only shows at NThe fix
Per-crew worker caps Crews doubled as units of parallelism, so crew 3 added 2 more concurrent workers against the same two subscriptions. At N=5 that's 10 workers and both vendors saturate at once. One global budget in capacity.json, split into per-wave grants. Adding a crew adds queueing, never load.
"Disjoint file scope" Hand-partitionable at N=2, impossible at N=5. Every crew eventually reaches for the lockfile, CI config, routes, migrations. docs/owners.md: one owner per path. Everything else needs a lease, one per glob at a time.
All traffic relayed through the program Pairs grow O(N²) while the relay stays serial and single-context. The portfolio manager becomes a switchboard. Handoff files are the channel. The program verifies and points; it never retells an interface in prose.
Merge order was nobody's A candidate tested as a set, then merged in whatever order a human picked — verifying a combination that may never exist. One integrator builds the real merge result, merges it, re-verifies, and reverts itself if the branch goes red.
Crew names hardcoded Adding a crew meant editing the roster, the init script, the backlog, the boundary map, the registries. nightshift-add-crew.sh clones and registers; registries and backlog sections are discovered, not enumerated.
The honest ceiling

N crews work only if the repo has N reasonably independent seams. Adding a crew to a codebase with two seams buys you three crews queueing on the same files. Crews scale with the architecture, not with ambition — and when the architecture is the limit, the report says so instead of quietly serialising everything.

The constraint everything is built around

A session can only message its own children

Omnigent lets a session dispatch work to its direct children and nowhere else. There is no sibling channel: no crew can reach another crew, and none can reach the shared functions. Everything crossing a boundary goes up to the program and back, or it gets written to a file.

That removes the failure mode that kills parallel delivery — two crews holding different beliefs about the same interface because they settled it in a conversation nobody recorded. Here, a cross-crew agreement has nowhere to live except a file.

Capacity is a budget, not a per-crew cap

The fix that makes N safe

Every crew's workers come out of one number. The program hands out grants each wave, and the grants must sum to the budget or less. Unequal grants are correct: the crew on the critical path gets more, a crew waiting on a handoff gets one or none, and a grant of zero is a real answer that means you are next, not now.

Who runs on which model

The reasoning tier, fable, costs roughly twice Opus per token — so it is spent exactly once, at discovery. product is the only Fable seat: discovery runs once, its output (the definition of done) is the fixed point every wave optimises toward, and it is the one artifact with a single author and no cross-vendor check behind it — architecture gets two competing drafts, the PRD does not. staff's one-time blind proposal gets Fable per-dispatch (args.model); its recurring ADR reviews do not. The program deliberately stays off it — a multi-day continuous session is the highest token volume of any seat, the most expensive possible home for a 2× model. Workers never see it: a worker gets more effort or a better-specified task, never a bigger model. security never runs on it at all — that tier's bug-finding gains exclude security analysis, and its safety classifiers decline most cybersecurity work, so the program treats a refusal as a reroute to a Claude or Codex seat, never a retry. The two discovery dispatches carry roughly double the usual cost_budget (12–16 vs 8), buying the same thinking depth at the 2× price.

One item, from charter to merged

Two independent gates before anything lands

Inside the crew, two vendors propose independently before anything is built, and the test plan is written from the criteria before the code exists. Then the PR leaves the crew entirely: a different crew reviews it. In-crew cross-vendor review catches defects; a reviewer from another crew catches a plan that only makes sense from inside one crew.

Round-robin, fixed, no negotiation

Crew i's PR is reviewed by crew i+1, wrapping. Fixed rotation spreads load, stays predictable, and — the real reason — makes reciprocity trading impossible: no crew can soften a review in exchange for a soft one back. Two exceptions only: skip a reviewer that would be reviewing its own interface, and use an idle crew anyway, since reviewing is the most useful thing a crew with a zero grant can do.

Anti-rubber-stamp

A review reporting nothing must still say what it checked and what it deliberately did not. "Looks good" is not a verdict. Every review is logged in .omni/reviews.md with its blocking count and loops-to-clean, and the retro reads that file to compute escaped defects — bugs found after a cross-crew review passed. That number is the only honest measure of whether this gate is real.

One writer of the default branch

Conditional, tested, reversible

With no human merging, the machine gates are all that stand between a bad diff and main. So merging is narrow and reversible: a single integrator, a real merge result tested before it lands, a tag before every attempt, and a self-revert if the branch goes red.

Branch protection, inverted

Protection requiring human approvals deadlocks every merge, because the integrator has no approver. Protection requiring status checks is ideal — it blocks a red merge without needing a person. preflight.sh fails the run if it finds the former and warns if it finds neither.

Where you watch it from your phone

GitHub is the tracker; the repo is the wiki

The org needs a Jira and a Confluence, and it already has both. Issues are the backlog — the single source of truth, with .omni/backlog.md demoted to a cached mirror for offline resume. A Projects v2 board is your glance view. And the PRDs, ADRs, specs, test cases and release notes the crews already write to docs/ render as the wiki, on a phone, with no sync to maintain.

The deciding argument was not features: it is that the box is already authenticated. Every alternative means another API token sitting on a machine that holds your Claude and Codex subscription credentials.

Decide, don't queue

There is nobody to escalate to, so an escalation queue would just be a stall. Every question gets decided, and the decision is recorded with what it rejected and what would reverse it. Where a choice is expensive to undo, the org takes the reversible variant and names what it gave up: ship behind a flag, add a column instead of rewriting one, keep the old path alive one more wave.

Two risks no mechanism covers

A wrong brief gets built, confidently, for days. Discovery makes this cheaper than it was — two vendors interrogate the brief, assumptions get written down, and milestone 1 must produce something demonstrable specifically so being wrong surfaces in days rather than weeks. But nothing questions the premise: the debate argues how, never whether. Reading the first report is what that costs you.

Agents verify against tests agents wrote. Cross-crew review and QA catch a great deal, but nobody checks against real users or real data. An escaped defect lands in main and stays there until someone notices.

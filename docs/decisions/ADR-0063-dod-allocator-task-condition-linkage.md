# ADR-0063: Task-to-DoD-condition linkage is a many-to-many join table with OR-of-paths admission; BLOCKED/MANUAL never fold into FAIL

Date: 2026-09-01 · Status: accepted
Deciders: program (cross-seam call, per `docs/owners.md` row for `docs/decisions/**`), staff (gate, required before crew_alpha builds on it)
Spec: GitHub issue #423 (root/tracking after this ADR's split), child issues #423-A (Observability), #423-B (Bookkeeping), #423-C (Enforcement)
Depends on: ADR-0025 (DoD close-out gate — BLOCKED vs FAIL is decision 1 there and is NOT reopened by this ADR), ADR-0032/ADR-0048 (`ready`/`plan` additive gating precedent), ADR-0033 (admission derivation writes only on `phase=='new'`)

## Context

Issue #423 wants the allocator to refuse normal implementation slots for tasks that are not on a path from an open DoD condition. Two independent, blind proposals already exist on the issue (2026-08-31 DoR pass, see `.omni/decisions.md` entry `~01:10Z` and the issue's own comment `#423#issuecomment-5473347010`):

- **crew_alpha (Claude side):** a single nullable `tasks.dod_condition_id` column. One task, one condition, no explicit combination rule because there is nothing to combine.
- **architect (Codex side):** a normalized `task_dod_links(task_id, condition_id, blocking_artifact)` table, multiple links per task via a `depends_on` condition-to-condition traversal graph, `BLOCKED`/`MANUAL` folded into `FAIL` with an optional `detail_status`.

`staff`'s adversarial review of both (same DoR pass) found the reconciling question neither draft nor the pm's own NOT-READY verdict answered: when a task carries more than one condition link, is it admitted because ANY linked condition is still open (OR-of-paths), or only when ALL are (AND-list)? It also flagged architect's `BLOCKED`/`MANUAL` → `FAIL` fold as **inconsistent-with ADR-0025**, which requires those stay distinct verdicts. That review is `needs-a-wider-decision` — this ADR is that decision, made by program per `docs/owners.md`'s cross-seam row, not re-litigated as a third blind dispatch, because the existing evidence already contains both vendor proposals in full (the instruction bar for a fresh two-vendor dispatch — "if the existing evidence does not already contain both" — is not met here).

Re-verified against `origin/main` at `f82559a7` (this ADR's own checkpoint, `nightshift-ctl checkpoint create --wave 423`, id 35) rather than trusting the issue body's 2026-08-30 snapshot: of the "8 documents + 3 manifest sections" the issue names, `DOD-MANIFEST.json` now has `preflight_checks` (landed since, condition 12's own work) — only `protected_capabilities` (D19) and `sentinel_test_node` (D20) remain absent. The 8 documents (`docs/audit/{CONCURRENCY,SURVIVAL,PIPELINE,BOUNDARIES,INSTALL}.md`, `docs/audit/FINDINGS.md`, `docs/HANDOVER.md`, `docs/prd/TRACEABILITY.md`) are still absent, confirmed via `git ls-tree -r --name-only origin/main`. That is **10** dispatchable items, not 11, and Issue #423-B's scope is sized to that recount, not the stale figure.

## Options considered

### A — Adopt crew_alpha's single-column model as-is (rejected)

Simplest migration (one additive nullable column, no new table). Rejected because it cannot express a task that legitimately advances more than one condition at once (e.g., a shared fixture-scaffold PR that unblocks both the `docs/audit/BOUNDARIES.md` write and the `sentinel_test_node` manifest entry D20 depends on) without either duplicating the task row's identity elsewhere or silently picking one condition and hiding the other — which is exactly the "open condition invisible to the allocator" defect #423 exists to fix, recreated one level down. AC-4's own wording, "on a path from an open DoD condition," is a path/graph concept in the singular-or-plural sense already; forcing it into a single foreign key answers a narrower question than the acceptance criterion asks.

### B — Adopt architect's full model as-is: `task_dod_links` + `depends_on` condition graph + BLOCKED/MANUAL folded into FAIL (rejected)

The join table is right (see Decision). The `depends_on` **condition-to-condition traversal graph** is rejected for now: nothing in the current 10-item backlog needs it. D20's dependency on D16 ("depends on condition 16's sink corpus, not yet enumerated" — `tests/dod_validate.py` line 879) is a **content** dependency between two audit documents, already expressible as an ordinary GitHub issue "Depends on" edge in Issue #423-B's sweep; it does not require the allocator itself to walk a condition graph to decide admission. Building unused traversal machinery now is exactly the larger, harder-to-reverse surface the safest-option principle exists to avoid — a bigger migration, more code for `staff`/reviewers to carry, and a rollback that means deleting graph-edges data as well as a table. The `BLOCKED`/`MANUAL` → `FAIL` fold is rejected outright and not a close call: ADR-0025 requires those verdicts stay distinct so `BLOCKED never counts as met` is still checkable independent of `FAIL`; collapsing them behind an *optional* `detail_status` lets a consumer that reads `verdict` alone over-gate on a condition that is merely unreachable, not actually failing — reintroducing the exact deadlock risk the pm's own AC-1 finding flagged.

### C — Many-to-many join table (architect's data shape, minus the graph), OR-of-paths admission, BLOCKED/MANUAL stay first-class (adopted)

Take architect's `task_dod_links(task_id, condition_id, blocking_artifact)` as the schema — it is the smallest structure that lets one task legitimately name more than one condition — but drop the `depends_on` traversal graph (see Option B) and the BLOCKED/MANUAL fold (inconsistent with ADR-0025). Admission is **OR-of-paths**: a task is "on a path from an open DoD condition" iff at least one of its linked `condition_id`s currently reports `verdict == FAIL` in the validator's `--json` output (Issue #423-A). A task linked to zero conditions is not on any path, full stop — that is the "neither (a) ... nor (b) from-owner, nor (c) incident" case AC-4 already names. `BLOCKED` and `MANUAL` conditions are reported in the JSON as their own verdicts, never coerced toward `FAIL` or `PASS`, and are separately surfaced as `unallocatable` per the issue's own empty-state clause — a task linked only to a `BLOCKED`/`MANUAL` condition is correctly NOT admitted by this gate (it has no `FAIL` path), and is visible in the heartbeat's unallocatable list rather than silently denied with no explanation.

## Decision

Adopt **C**.

- New table, created inside `bin/nightshift-ctl`'s own embedded `SCHEMA` string (there is no `db/migrations/**` directory in this repo — corrected per staff's 2026-09-01 review, which cited `bin/nightshift-ctl:236-470` and the real precedent at `bin/nightshift-ctl:439-442`, migration sequence 8 for #424/ADR-0055). `bin/nightshift-ctl` is `crew_alpha`-owned, single-writer, per `docs/owners.md`; the sequence number comes from `nightshift-ctl seq next --name migrations` allocated under crew_alpha's own SERIALIZE lease on `bin/nightshift-ctl` (self-held, the same mechanism migration sequence 8 already uses — not a cross-crew grant from `platform`, which owns no part of this path). **#423-A creates this table** (dormant — see below), so #423-C's build never has to create it against a stale precondition: `task_dod_links(id, task_id, condition_id TEXT, blocking_artifact TEXT, created_at)`. No change to the existing `tasks` schema.
- `tests/dod_validate.py --json` (Issue #423-A) emits, per condition: `{id, verdict, reason, blocking_artifact}` — `blocking_artifact: null` when a `FAIL` has none derivable, `verdict` is exactly one of `PASS|FAIL|BLOCKED|MANUAL` (ADR-0025's four, untouched), plus top-level `dod_complete: bool`, `manifest_readable: bool`, `unallocatable: [condition_id, ...]` (FAIL-with-null-artifact plus every BLOCKED/MANUAL). Human-readable stdout is unchanged when `--json` is absent (AC-2).
- `bin/nightshift-ctl ready` (Issue #423-A, non-gating) gains an additive computed field per task — `on_dod_path: bool`, `linked_conditions: [...]` — derived by joining `task_dod_links` against the last-ingested `--json` snapshot (`nightshift-ctl dod ingest`, idempotent: re-ingesting the same JSON upserts by `condition_id`, never duplicates rows). This ships wired **dormant**: Issue #423-A must not change what any command admits or denies (staff's finding on crew_alpha's draft — the guard stays inert until #423-C explicitly activates it, closing the ambiguity staff flagged about whether it ships live). `task_dod_links` is created **empty** by #423-A (see above) — the join is exercised (read-only) by `ready`'s new fields the moment #423-A ships, but nothing links a real task to a condition until a task is deliberately given one, so the field reads `on_dod_path: false, linked_conditions: []` for every task until further, separate work populates rows. #423-C's later activation reads the same table; it does not create it.
- `bin/nightshift-ctl` (Issue #423-C only, not this wave — see Consequences) denies a normal slot when `on_dod_path` is false and the task carries neither `from-owner` nor `incident`, exiting 3 with `{"denied": "not_on_dod_path"}` in its JSON, additive inside the existing `_derive_normal_phase` `phase=='new'` branch per ADR-0032/ADR-0048 precedent, not a parallel gate.
- `dod_manifest_unreadable` fails closed (denies), `dod_complete: true` admits any well-formed task, exactly as the issue's own failure/empty states specify — this ADR does not change those, it only fixes how multiple links combine.

## Consequences

- Issue #423 is re-scoped to a tracking issue and split into three children with explicit dependency edges, per the pm's own DoR recommendation (`#423#issuecomment-5473347010`) and per this turn's owner authorization to create exactly the issues needed to separate observability, bookkeeping, and enforcement:
  - **#423-A (Observability, non-gating, size M):** `--json` output, `dod ingest`, the new (empty, dormant) `task_dod_links` **and** `dod_conditions` snapshot tables, additive `ready` field, heartbeat DoD delta line, two-consecutive-zero-delta escalation. No admission behaviour changes. Depends on: nothing new beyond its own self-held SERIALIZE lease on `bin/nightshift-ctl` (crew_alpha's own file, ordinary discipline, not a cross-crew ask).
  - **#423-B (Bookkeeping, size S, no code):** one dispatchable GitHub issue per currently-open condition lacking one — 10 items today (recounted above), each naming its `blocking_artifact` and, for D20, an explicit "Depends on #423-B/D16" edge to the D16 issue rather than a code-level condition graph. Depends on: nothing (pure tracker bookkeeping).
  - **#423-C (Enforcement, size M, real rollout, `needs-a-wider-decision` per staff until this ADR + an explicit cross-crew sign-off thread cover it — not routed through issue #443's Project Contract tooling, which is itself unbuilt and would be a circular blocker):** the live gate wired against the `task_dod_links` table #423-A already created, a rollback/kill-switch readable at gate-check time (not just deploy-time — pm/staff's own missing-AC finding). No new cross-crew lease is needed here (corrected — see Decision: there is no `db/migrations/**` path in this repo and no platform grant to acquire; crew_alpha uses its own ordinary self-serialize discipline on `bin/nightshift-ctl`). **Depends on #423-A** (needs the JSON/ingest data and the table to exist) **and #423-B** (activating the gate before every open condition has a linked issue would deny ALL normal work with nothing to link new tasks to — a total-lockout failure mode neither vendor draft named, found by program while sequencing this ADR's consequences).
- This wave builds and ships #423-A end to end (implementation, tests, cross-vendor review, cross-crew review, PM acceptance, release) and completes #423-B's sweep directly as program tracker bookkeeping (no code, no crew dispatch needed). #423-C is filed, DoR'd against this ADR, and explicitly queued — its migration-lease and wider-sign-off needs make it the wrong size for this turn, not a blocker; recorded in `.omni/decisions.md`.
- `#423` itself stays open as the tracking issue until #423-C merges; it is not closed by #423-A alone.

## Rejected alternatives (summary)

- Option A (single-column, AND-implicit): cannot express one task serving multiple conditions; recreates the invisibility defect #423 fixes.
- Option B in full (condition-graph traversal + BLOCKED/MANUAL fold): the graph traversal solves a problem with zero current instances in the 10-item backlog (rejected on safest-reversible grounds, revisit if that changes — see Reversal trigger); the fold is inconsistent with ADR-0025 and rejected outright regardless of the graph question.

## Reversal trigger

If, within one wave of #423-C's activation, a real task needs admission to depend on a **condition-to-condition** relationship (not a task-to-condition one) — e.g., "this task may only close condition X once condition Y's prerequisite artifact exists" — reopen this ADR's Option B and adopt architect's `depends_on` graph as a superseding ADR. Until that need is observed with a real task, the flat join table stays. Separately: if OR-of-paths admits a task whose only open link never actually moves that condition toward PASS across two consecutive DoD ingests, treat that as evidence the per-task `blocking_artifact` is mis-derived, not as evidence against OR semantics itself, and fix the derivation first.

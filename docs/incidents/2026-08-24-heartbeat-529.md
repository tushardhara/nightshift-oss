# 2026-08-24 — three hourly heartbeats lost to a transient vendor 529

`Refs #132` `Refs #42`

## What happened

The hourly scheduled task `f3e532fd631045858aa386a26405d56a` ("Nightshift hourly
heartbeat") is the only mechanism that returns this org to its objective after a
session ends. On 2026-08-24 it failed three times in a row:

```
08-24 03:00Z succeeded  -
08-24 04:00Z failed     runner_error
08-24 05:00Z failed     runner_error
08-24 06:00Z failed     runner_error
08-24 07:00Z succeeded  -
```

(pulled from `GET /v1/scheduled-tasks/{id}/runs`; the issue records 05:00Z and
06:00Z — 04:00Z failed as well.)

Root cause is established and is not re-litigated here: correlated upstream
Anthropic `529 Overloaded`, recorded in `#132#issuecomment-5391417179`.

## The observation this file exists to record

**A single transient 529 must not cost this org an hour.**

That is not a statement about vendor reliability, it is a statement about the
shape of our own recovery. The scheduler recorded the failure immediately, with
an `error_code`, and then did the only thing it knew how to do: wait for the
next hourly tick. There was no retry, so one refused HTTP request bought a full
hour of silence — and three of them bought three.

Two consequences follow, and both are design constraints rather than opinions:

1. **Retry belongs below the agent layer.** The failure happened *at dispatch*,
   before any model call. Nothing inside the turn could have retried it, because
   no turn existed. Recovery therefore has to live in something that is watching
   from outside — which is why the retry in this repo lives in
   `deploy/nightshift-scheduler-probe.py` under the watchdog timer, and not in
   any prompt.

2. **The cost of a missed wake-up is bounded by how often we look, not by how
   often the task is scheduled.** An hourly task checked hourly has an hourly
   worst case. The watchdog timer now runs every 10 minutes
   (`deploy/systemd/nightshift-watchdog.timer`), which is what makes a re-fire
   able to recover the *current* hour rather than merely reporting that it was
   lost.

## What made it expensive, which is the part worth remembering

Nobody noticed for an hour. The only reason it was noticed at all is that an
earlier driver session happened to still be awake and looking.

That is the real defect, and it is worse than the outage: the detection path ran
*inside* the thing that had failed. A monitor that needs the loop alive in order
to notice the loop is dead has not been built yet — it has only been described.
Everything in `#132` follows from that, and it is why the detector is required
to work with zero model calls and no agent session alive.

## Bounds on the retry, and why each one is there

Re-firing production work automatically is a real hazard, so the retry refuses
more often than it fires (`deploy/nightshift-scheduler-probe.py`, `maybe_retry`):

| bound | why |
| --- | --- |
| only when `state` is `active` | a paused task is a deliberate instruction; re-firing it overrides the owner |
| only the current scheduling period | re-running a three-hour-old slot re-runs stale instructions |
| never while a run is `running` | never double-drive the org |
| at most N attempts **per period** | keyed on the period, not the run row — a re-fire mints a *new* run row, so a per-run key reset the cap on every attempt and bounded nothing |
| exponential backoff from the last **attempt** | a vendor that is still overloaded must not be hammered; measuring from the newest failure instead restarted the clock every time |
| an attempt that the scheduler *rejects* still spends budget | otherwise a scheduler answering 500 becomes an unbounded loop |

The fifth and sixth rows were found by running the probe against the live
scheduler, not against a fixture. Fixtures hold the run history still; a real
scheduler appends to it, and that difference is exactly what made the cap
ineffective. It is worth assuming that any retry tested only against a fixture
has this bug.

## What is deliberately NOT retried

A `launch_failed`, a missing task row, or a task that has been paused are not
transient and a retry cannot fix any of them. They alert and stop. Retrying
every failure class would convert a loud, actionable fault into a quiet loop.

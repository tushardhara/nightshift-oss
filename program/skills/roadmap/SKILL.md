# roadmap — plan with the crews, not at them

## Procedure

1. **State the wave's outcome** with a completion condition you could actually
   check. The goal itself is already in `.omni/goal.md` — GENERATED by discovery,
   never re-authored here — so read it, including its coarse dependency graph
   (discovery Step 3b: outcome-shaped slices with `depends_on` edges), and state
   this wave's slice of it in the charters. Scope every charter this wave to the
   graph's CURRENTLY-ACTIONABLE node(s) only — no unmet `depends_on` — never a
   node still gated on one, however idle a crew is; if more than one node is
   actionable at once, rank them by the existing priority order
   (`unblocks-other-work > user-visible-breakage > committed-outcome > new-value
   > cleanup`). "Ship the billing rewrite" is not an outcome; "invoices generate
   from the new schema, old and new agree on last quarter's data, and the old
   path is behind a flag" is.

2. **Ask each crew for an independent plan.** Dispatch every crew with
   `purpose: "explore"` and the same goal brief. Ask each for: how it would split
   the work, which files and subsystems it would own, what it needs from another
   crew, the riskiest unknown, and what it would cut first under pressure.

   Same brief to each, no cross-talk. Dispatch in one turn, end the turn, collect
   from `sys_read_inbox`.

3. **Reconcile into boundaries.** The plans will overlap. Where two crews both
   claim a subsystem, decide the owner — do not split a file between crews.
   Where both plans skip something, that gap is yours to assign. Write the
   boundary map into `.omni/goal.md`: crew → owned paths → owned interfaces.
   Disjoint file scope is what makes parallel crews safe.

4. **Sequence the dependencies.** Identify what crew B cannot start until crew A
   hands off. Prefer giving B independent work in wave 1 over having it wait. If
   both crews must touch one interface, one crew defines it and hands it off; the
   other consumes. Never let two crews design the same interface in parallel.
   Where the dependency is between two ordinary backlog items rather than a live
   handoff, mirror it into the control plane as soon as both items have task rows
   (`nightshift-ctl task dependency-add --id <dependent>-build --depends-on
   <prereq>-build`, #219, ADR-0048) — a dependency that exists only as prose in
   this file is invisible to step 5's READY gate below.

5. **Charter each crew.** THE READY QUEUE GATES THIS STEP (#219, ADR-0048): every
   DoR-passed candidate should already be registered as a `pending` task row (the
   TRACKER step in `program/config.yaml` does this at DoR time — register it here
   too if a candidate reached this step without it). Run `nightshift-ctl task
   ready` fresh and charter ONLY the items that call returns — never an item that
   looks finished in GitHub prose but is not in that set (missing size, blocked,
   cycle-bound, or pending `L` — `needs_split`, never auto-split here). A coarse
   graph node (step 1 above) is typically filed as exactly one `size:L` issue per
   currently-actionable slice, so it hits this same gate on arrival. A stuck
   `needs_split` item is not simply skipped forever: hand it back to the owning
   crew's `pm` to decompose per its own Definition of Ready criterion 7 (#220,
   ADR-0049) into a dependency graph of S/M child issues, the same way any other
   DoR gap returns to the top of the queue — only those children, registered with
   their own task rows and any real dependency edges, can ever appear in this set,
   never the L parent itself. The coarse graph changes which node becomes an
   issue and when; it never changes how an oversized issue turns into executable
   work — that stays the existing #220/ADR-0049 mechanism, unmodified. Where the
   READY set is larger than this wave's grant,
   charter the top-ranked items first
   by the existing order — `unblocks-other-work > user-visible-breakage >
   committed-outcome > new-value > cleanup` — pooled across crews, since cross-
   crew priority is the program's call. If the normal-implementation READY set is
   empty for a crew, do not charter unrelated or unready work to fill its grant;
   give it review/handoff work instead and say so, same as the `NEVER IDLE`
   carve-out in `program/config.yaml`. One charter per crew per wave:
   ```
   Outcome: <what is true when this wave is done>
   Task ID: <the exact id from nightshift-ctl task ready, e.g. 219-build — the
             crew's own Phase 1 task upsert reuses this id, never a new one>
   Owned paths: <explicit list>
   Interfaces: <owns / consumes, with handoff expected>
   Acceptance: <criteria, testable>
   ADRs required: <decisions this crew must record before building>
   Grant this wave: <workers, items in flight — from the ONE global budget in
                     .omni/capacity.json; grants across crews sum to it or less>
   Budget: cost_budget {max_cost_usd: 133}    # no ask_thresholds when unattended
   Out of scope: <explicit>
   ```

6. **Commit the plan and proceed** (unattended mode — nothing waits on a human).
   Write the boundary map, the wave-1 charters, and every crew disagreement you
   resolved into `.omni/ledger.md` and `.omni/STATUS.md`, naming which call was
   yours and what the losing option was. A contested boundary that you cannot
   settle from evidence goes to `.omni/decisions.md` with your recommendation,
   and you take the reversible option meanwhile.

7. **Record it.** An ADR for every structural decision in the map (ownership
   splits, interface shape, sequencing that costs a crew idle time). Append the
   wave plan to `.omni/ledger.md`. Six months on, "why does crew_beta own the
   scheduler?" must be answerable from files, not memory.

## Notes

- Two crews is the practical maximum running concurrently on subscription
  credentials. A third crew mostly buys you rate-limit collisions.
- Re-run this skill at each wave boundary, not once at project start. Plans decay;
  the ledger of why they changed is what keeps the project explicable.
- If a crew's plan reveals the goal itself is wrong, do not charter around it.
  Write the contradiction to `.omni/decisions.md` and `STATUS.md` in full, then
  charter only the work that holds regardless of how that question resolves. This
  is the most valuable output this phase can produce — make sure it is impossible
  to miss.
- Never expand a coarse graph node (discovery Step 3b) into issues or S/M tasks
  merely because a crew has spare grant. Only the currently-actionable node(s)
  get decomposed; an idle crew with nothing actionable gets review/handoff work
  per `program/config.yaml`'s NEVER IDLE carve-out, never a head start on a
  slice still gated by an unmet `depends_on`.
